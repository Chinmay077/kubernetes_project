A

Request Routing

See which Pod handles each request

▼

📚 Concept

When you access MiniMart via the NodePort Service, kube-proxy intercepts the TCP connection and forwards it to one of the healthy frontend Pods using iptables rules. The Service does not guarantee round-robin; it uses random selection by default.

🧪 Try it

  1. Click Send Request above multiple times.
  2. Watch the Last FE Pod and Last BE Pod change.
  3. Open your terminal and run:
# Watch pods receive requests in real time
kubectl logs -l app=minimart-frontend --all-containers -f --prefix

# In another terminal, run curl 10 times
for i in $(seq 1 10); do curl -s http://$(minikube ip):30080/api/proxy/info | python -m json.tool; done

✅ Expected Outcome

You should see requests landing on different Pods. The pod name in each response may repeat (not every request hits a new Pod).

B

Scaling

Scale replicas up and observe Pod distribution

▼

📚 Concept

A Deployment defines a desired number of replicas. The ReplicaSet controller watches the cluster and continuously reconciles the actual Pod count with the desired count. Scaling simply changes the replicas field.

🧪 Try it

# Scale frontend to 5 replicas
kubectl scale deployment minimart-frontend --replicas=5

# Watch pods appear (keep this terminal open)
kubectl get pods -l app=minimart-frontend -w

# Verify new pods are Running
kubectl get pods -l app=minimart-frontend

# Scale back down
kubectl scale deployment minimart-frontend --replicas=3

✅ Expected Outcome

You'll see 2 new Pods appear with status ContainerCreating → Running. After scaling down, 2 Pods will be Terminating. The Deployment always maintains the desired count.

C

Self-Healing

Delete a Pod and watch Kubernetes recreate it

▼

📚 Concept

A Pod managed by a Deployment is ephemeral. If you delete it, the ReplicaSet controller detects the deficit and schedules a replacement. This is the "self-healing" loop.

Deployment → ReplicaSet → Pod (deleted) → ReplicaSet notices → New Pod scheduled

🧪 Try it

# List current frontend pods
kubectl get pods -l app=minimart-frontend

# Copy one pod name from the output above, then:
kubectl delete pod <paste-pod-name-here>

# Watch in another terminal:
kubectl get pods -l app=minimart-frontend -w

# The deleted pod shows Terminating, a new one appears immediately

✅ Expected Outcome

The deleted Pod is replaced within seconds. Your application never goes fully offline because the other 2 replicas continue serving traffic during the brief Pod restart.

🟡 Simulated — NOT a real kubectl delete
D

Load Balancing

Observe traffic distribution across Pods

▼

📚 Concept

Kubernetes Services use iptables rules (or IPVS) for load balancing. The algorithm is random selection across endpoints, not strict round-robin. With small request counts you may see uneven distribution — this is expected.

🧪 Try it

Pod Hit Distribution 🟢 Live

✅ Expected Outcome

After 20 requests, distribution will be approximately even but rarely perfect. This proves that Kubernetes does not guarantee strict round-robin.

E

Health Checks

Understand liveness vs readiness probes

▼

📚 Concept

  • Liveness probe → Is the container still alive? If it fails, Kubernetes restarts the container.
  • Readiness probe → Is the container ready to receive traffic? If it fails, the Pod is removed from the Service's endpoint list but is NOT restarted.

kubectl Cheat Sheet

Inspect

kubectl get pods
kubectl get services
kubectl get deployments
kubectl describe pod <name>
kubectl get events -w

Logs

kubectl logs <pod-name>
kubectl logs -l app=minimart-backend -f
kubectl logs --previous <pod-name>

Scale & Update

kubectl scale deployment minimart-frontend --replicas=5
kubectl rollout status deployment/minimart-frontend
kubectl rollout undo deployment/minimart-frontend

Debug

kubectl exec -it <pod-name> -- /bin/sh
kubectl port-forward svc/minimart-backend-svc 5000:5000
kubectl top pods
